Lead Intelligence Agent

A local, conversational, retrieval-augmented agent that ingests sales leads, indexes them for hybrid (semantic + structured) search, and answers natural-language questions through a command-line interface. This document is a complete build specification: given only this file, an engineer or LLM should be able to reconstruct the system exactly as designed.

4. Key design decisions & rationale

4.1 Hybrid retrieval: metadata filter + semantic search

Embeddings capture fuzzy meaning; they cannot reliably enforce boolean or numeric constraints. "Companies with more than 500 employees" is arithmetic, "high priority" is boolean, "list all Directors" is exhaustive — none are semantic. Therefore:

  • Hard constraints (industry, company_size, high_priority, location, job title, lead source) → structured metadata filters applied by Chroma.
  • Soft intent (pain points, interests, tech needs from notes/tags) → semantic vector search.
  • Order: filter first to narrow the candidate set, then rank semantically within it.
Metadata is authoritative. high_priority (and industry, size, etc.) are stored as real, filterable metadata fields. A human-readable "High Priority Lead" prefix may also be included in the embedded text for readability, but the filter is what guarantees correctness.

4.2 Embedded text format

Each lead is embedded as a natural-language profile string (not raw JSON), because prose embeds better than braces/keys:

"[High Priority Lead] {first} {last}, {job_title} at {company} "
"({industry}, {company_size} employees, {location}). "
"Notes: {notes}. Tags: {tags}. Tech: {tech_stack}."

The [High Priority Lead] prefix is included only for priority leads and kept short to avoid clustering all priority leads together in vector space.

4.3 We own the embeddings

Embeddings and reranking run locally via sentence-transformers. We do not rely on ChromaDB's default embedding function; instead we pass our own so the same model is guaranteed to be used at ingest and query time (mismatched embedders is the classic silent RAG bug).

OpenRouter does not serve embeddings. OpenRouter provides the chat LLM only. All embedding and reranking is local. This split is intentional and consistent with "runs locally."

4.4 Cross-encoder rerank + threshold (relevance protection)

Top-k vector search always returns k documents even when nothing is truly relevant. To prevent returning nonsense:

  1. Over-fetch a wider candidate set from the vector store (e.g. top 20).
  2. Rerank each (query, candidate) pair with a cross-encoder (more accurate at true relevance than cosine).
  3. Threshold: drop candidates below a calibrated score; keep the top k.
  4. If nothing survives, return an empty (but successful) result — this is not an error.

This is the pragmatic cousin of Corrective-RAG (CRAG). It is self-correcting within a query, not self-improving over time (that is the Part 3 feedback loop).

4.5 LangGraph (not plain LangChain) for orchestration

The retrieval correction lives inside the tool, but the summarize-every-N-turns memory logic is custom conditional control flow over conversation state — exactly what LangGraph models cleanly. We use LangGraph's prebuilt ReAct agent plus a custom summarization node, with LangChain components (chat model, tool definitions) used inside the graph. It is not either/or.

4.6 LLM via OpenRouter (Anthropic Claude)

The agent's LLM is an Anthropic Claude model served through OpenRouter, accessed with ChatOpenAI pointed at base_url="https://openrouter.ai/api/v1" using an OpenRouter API key. Claude models support tool/function calling, which the ReAct agent requires.

4.7 Response structure & the three data audiences

The agent returns a typed object: { summary: str, leads: list[Lead] }.

The LLM writes only the summary. The leads array is attached verbatim from the tool output. Never let the LLM regenerate lead data — it will drop or alter fields (hallucinated lead data is unacceptable in a lead tool).

Lead data has three distinct audiences, treated differently to control context growth:

AudienceWhat they get
The user (CLI)Full {summary, leads} — everything.
The LLM, within the current turnFull tool output (needs fields transiently to write the summary). Lands as a LangGraph ToolMessage.
Persisted conversation memoryCompact stub only — id, name, company per returned lead (plus the summary). Not full blobs. Enables follow-ups ("the Texas ones", "the second one") without bloating context; details are re-fetched by id on demand.

4.8 Memory & summarization

  • Short-term thread memory enables follow-up questions (required).
  • After N turns, a summarization node condenses older messages into a running summary and trims them, keeping summary + last few messages.
  • Conversation state is persisted to a local JSON file so a session can be inspected/resumed.
  • Summaries condense dialogue and compact lead stubs — never full retrieved blobs.

5. Component design & contracts

Everything is statically typed with pydantic where possible. Illustrative signatures below (not final code).

5.1 Settings — settings.py

pydantic-settings.BaseSettings, loaded from environment / .env. Missing required values (e.g. API key) fail fast at load with a clear message.

class Settings(BaseSettings):
    openrouter_api_key: str
    llm_model: str = "anthropic/claude-3.5-sonnet"
    embedding_model: str = "all-MiniLM-L6-v2"
    cross_encoder_model: str = "cross-encoder/ms-marco-MiniLM-L-6-v2"
    leads_path: Path = Path("leads.json")
    chroma_path: Path = Path(".chroma")
    collection_name: str = "leads"
    top_k: int = 5
    overfetch: int = 20
    rerank_threshold: float = 0.0        # calibrate empirically
    summarize_every_n_turns: int = 6
    memory_path: Path = Path("memory/session.json")

5.2 Domain models — models.py

class Lead(BaseModel):
    id: int
    first_name: str; last_name: str
    email: str; job_title: str
    company: str; company_size: int
    industry: str; location: str; website: str
    tech_stack: list[str]; lead_source: str
    last_contacted: str; notes: str; tags: list[str]
    high_priority: bool = False          # computed at load

    def to_embedding_text(self) -> str: ...   # pure; the profile string
    def to_metadata(self) -> dict: ...        # filterable fields for Chroma

class ScoredLead(BaseModel):
    lead: Lead
    score: float

class SearchResponse(BaseModel):
    summary: str
    leads: list[Lead]

Note: Lead deliberately has no .embed() method — producing a vector requires the ML model, which belongs to SemanticEngine, not the data object. Lead only knows how to describe itself as text and metadata.

5.3 Data loading — data.py

  • load_leads(path) -> list[Lead]: read JSON, validate each record into Lead, compute high_priority.
  • Raises a clear, typed error on: file missing, invalid JSON, or schema mismatch.
  • No industry normalization.

Single owner of both sentence-transformers models.

Wraps a Chroma PersistentClient. Uses the SemanticEngine so embeddings are consistent. Owns idempotent ingest.

5.6 Retrieval function — retrieval.py

Thin orchestration the tool calls (a function, not a class, by decision).

def retrieve(query, filters, store, engine, settings) -> list[ScoredLead]:
    candidates = store.query(query, filters, limit=settings.overfetch)
    reranked   = engine.rerank(query, candidates)
    return [c for c in reranked if c.score >= settings.rerank_threshold][: settings.top_k]

5.7 The tool — tools.py

A single LangChain tool, search_leads, exposed to the agent. Typed arguments become the JSON schema the LLM sees; the docstring instructs how to populate them.

Industry = Literal["Financial Services", "Education", ... all 29 ...]
LeadSource = Literal["Inbound - demo", ... all 8 ...]

@tool
def search_leads(
    query: str,
    industry: list[Industry] | None = None,     # OR-matched ($in); LLM maps colloquial terms
    lead_source: list[LeadSource] | None = None,
    min_company_size: int | None = None,
    location_contains: str | None = None,
    job_title_contains: str | None = None,
    high_priority: bool | None = None,
    top_k: int = 5,
) -> dict:
    """Search sales leads. Put HARD constraints (industry, size, priority,
    title, source, location) in the filter args; put descriptive INTENT
    (pain points, interests, tech) in `query`. Map colloquial terms to the
    allowed industry values and include related variants, e.g. 'fintech'
    -> ['Financial Services', 'Fintech']."""

Tool return contract (empty vs error are distinct)

SituationReturn
Results found{"status": "ok", "leads": [ ... ]}
Nothing passed threshold{"status": "ok", "leads": []} — not an error; agent narrates "no relevant leads".
Retrieval/store failure{"status": "error", "message": "There was an issue retrieving results from the data store."}

5.8 Prompts — prompts.py

System prompt establishes the agent's role, lists the enumerable field values, explains the colloquial→enum mapping guidance, and specifies that the final answer summary should be a concise, human-readable observation over the returned leads.

5.9 Memory — memory.py

  • Produces/updates a running summary; trims old messages.
  • Persists {summary, compact_lead_stubs, recent_messages} to local JSON.
  • Provides compact stubs (id/name/company) for follow-up resolution.

5.11 CLI — cli.py + main.py

  • REPL loop: read question → agent.query() → print summary + formatted lead list.
  • Top-level error boundary: any intermediate failure prints "Your request could not be responded to due to an error, please try again later." and logs the real error.
  • Graceful Ctrl-C/EOF exit.
  • main.py is a thin entrypoint: build settings → load data → build components → ingest → start REPL.

6. End-to-end data flows

Startup / ingestion

  1. Load & validate Settings (fail fast if API key missing).
  2. load_leads() → list[Lead] with high_priority computed (fail fast on file/parse/schema errors).
  3. Build SemanticEngine and LeadVectorStore.
  4. If the collection is empty: build profile text + metadata per lead, embed, and upsert. Otherwise skip (idempotent).
  5. Build LeadAgent; enter the CLI REPL.

Per query

  1. User types a question → LeadAgent.query().
  2. ReAct agent node (Claude via OpenRouter) decides whether/how to call search_leads, decomposing the question into filters + semantic query.
  3. Tool calls the retrieval function → vector store query (filter + vector, over-fetch) → cross-encoder rerank → threshold → top-k.
  4. Tool returns the typed contract (ok/empty/error).
  5. Agent writes a concise summary; code assembles SearchResponse with leads verbatim.
  6. CLI prints summary + leads. Compact stubs enter memory.
  7. Every N turns, the summarization node compresses history and persists JSON.

7. Error handling

FailureBehaviour
Missing/invalid OPENROUTER_API_KEYFail fast at settings load with clear message; non-zero exit.
leads.json missing / invalid JSON / wrong shapeFail fast before starting the agent, with a specific message per case.
First-run model download fails (network)Clear "could not download model" message; documented in README.
No results after rerank/thresholdNot an error — empty successful result; agent narrates "no relevant leads found".
Retrieval/vector-store failure during a queryTool returns status: error; agent surfaces that a data-store issue occurred.
Any intermediate failure (tool exec, LLM/OpenRouter call, etc.)Top-level boundary → "Your request could not be responded to due to an error, please try again later." Real error logged.
Ctrl-C / EOFClean exit, no traceback.

8. Configuration & defaults

All tunables live in Settings (see 5.1). Defaults: bi-encoder all-MiniLM-L6-v2 (384-dim, fast); cross-encoder ms-marco-MiniLM-L-6-v2; top_k=5; overfetch=20; summarize_every_n_turns=6; rerank_threshold calibrated empirically. Secrets via .env; never hardcoded.

  • Part 1: workflow diagram (Mermaid, see §3) + short written note on why agentic RAG beats a rules-based RPA/SQL filter (semantic intent in free-text notes, combined structured+fuzzy queries, conversational follow-ups — none expressible as predefined SQL rules).

  • Part 3 (bonus):
    • Metrics: retrieval precision (share of returned leads judged relevant — directly measurable via the cross-encoder/grader) and answer helpfulness / task success.
    • Orchestration: add a second agent when responsibilities diverge — e.g. a dedicated retrieval/grading agent separate from an answer-synthesis or query-planning agent.
    • Improvement: collect thumbs up/down + which leads the user engaged with; use it to tune the threshold, prompts, and (later) fine-tune retrieval — the genuine self-improvement loop.
